# 03 — Database Design

PostgreSQL 17.5. Schema is owned by Flyway; `ddl-auto: none` (`application.yml:23`), so Hibernate
never creates or alters a table. **Columns below are sourced from the migration files**, and any
place the Java annotation disagrees is called out.

## Storage topology

Two kinds of schema exist in the database. Only one is used.

| Schema | Tables | Used at runtime? |
|---|---|---|
| `public` | `tenants`, `users`, `categories`, `products`, `stock_mvts`, `flyway_schema_history` | **Yes — all queries go here** |
| `tenant_<company_code>` | `categories`, `products`, `stock_mvts`, `flyway_schema_history` | **No** |

`spring.flyway.locations` is `classpath:db/migration/common` and `schemas: public`
(`application.yml:40-41`). That is the only Flyway run the application performs at startup.

A `tenant_<code>` schema is created and migrated when a tenant is approved
(`ProvisioningServiceImpl.java:87-92,110-126`), using a second, programmatic Flyway pointed at
`classpath:db/migration/tenant`. Nothing ever queries those schemas: in `filter` mode Hibernate is
not multi-tenant-aware and every connection stays on `public`.

**So the isolation boundary is a column, not a schema.** Every business row carries `tenant_id`,
and the Hibernate `tenantFilter` appends `tenant_id = :tenantId AND deleted = false` to queries
(`AbstractEntity.java:29-33`). Rows for all tenants sit side by side in the same tables. If the
filter is not applied — see 02 — there is nothing else stopping a cross-tenant read.

## Entity reference

### `tenants`

| `tenant_id` | VARCHAR(255) | NO | Inherited. Holds the **company code**, not a UUID. See warning below. |
| `created_at` | TIMESTAMP | NO | |
| `updated_at` | TIMESTAMP | YES | |
| `created_by` | VARCHAR(255) | NO | |
| `updated_by` | VARCHAR(255) | YES | |
| `deleted` | BOOLEAN | NO | default `FALSE` |
| `company_name` | VARCHAR(255) | NO | |
| `company_code` | VARCHAR(255) | NO | UNIQUE `uc_tenants_company_code` |
| `email` | VARCHAR(255) | NO | UNIQUE `uc_tenants_email` |
| `status` | VARCHAR(255) | NO | default `'PENDING'`, CHECK `chk_tenant_status` |
| `admin_full_name` | VARCHAR(255) | NO | |
| `admin_email` | VARCHAR(255) | NO | UNIQUE `uc_tenants_admin_email` |
| `admin_username` | VARCHAR(255) | NO | UNIQUE `uc_tenants_admin_username` |
| `admin_password` | VARCHAR(255) | NO | BCrypt hash |

> **`tenants.tenant_id` holds a company code.** `AbstractEntity.onCreate` special-cases `Tenant`
> and sets `tenant_id = company_code.toLowerCase()` (`AbstractEntity.java:73-77`). Every other
> table stores the tenant's **UUID** there. The same column name carries two different kinds of
> value.

**The tenant's admin credentials are stored twice.** `admin_username`, `admin_email` and
`admin_password` live on the tenant row, and approval copies them into a `users` row
(`TenantServiceImpl.java:176-191`). They are never kept in sync afterwards.

### `users`

Source: `V1__init_Common_tables.sql:53-91`. Entity: `entities/User.java`.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | VARCHAR(255) | NO | PK `pk_users` |
| `tenant_id` | VARCHAR(255) | NO | Inherited. Holds `tenants.id` (UUID). **No FK.** |
| `created_at` / `updated_at` / `created_by` / `updated_by` / `deleted` | — | — | as above |
| `"tenant id"` | VARCHAR(255) | YES | **Column name contains a space.** FK `fk_user_tenant_id` → `tenants(id)` |
| `username` | VARCHAR(255) | NO | UNIQUE `uc_users_username` — **global, not per tenant** |
| `email` | VARCHAR(255) | NO | UNIQUE `uc_users_email` — also global |
| `password` | VARCHAR(255) | NO | BCrypt hash |
| `first_name` | VARCHAR(255) | NO | |
| `last_name` | VARCHAR(255) | NO | |
| `role` | VARCHAR(255) | NO | CHECK `chk_user_role` |
| `enabled` | BOOLEAN | YES | |

> **Migration and Java disagree here.** The migration puts the foreign key on `"tenant id"`
> (`V1:89-91`) and its own comment says the join column is `"tenant id"` (`V1:49`). The entity maps
> the `@ManyToOne` to **`tenant_id`** instead (`User.java:25-27`). Result: two tenant columns on
> `users`. `tenant_id` is what the application reads and writes; `"tenant id"` is the one with
> referential integrity, and **no entity maps it**. Only the seed data fills it
> (`V3__seed_demo_data.sql:37`).

Two further mismatches:

- `enabled` is nullable in the migration but a primitive `boolean` in Java (`User.java:50`). A
  `NULL` row would fail to load.
- `username`/`email` uniqueness is global. Two companies cannot both have a user called `admin`.
  Intentional for login — see 02, decision 9 — but it leaks one tenant's usernames to another
  through registration conflicts.

### `categories`

Source: `V5__init_tenant_business_tables.sql:17-31`. Entity: `entities/Category.java`.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | VARCHAR(255) | NO | PK `pk_categories` |
| `tenant_id` | VARCHAR(255) | NO | indexed, `idx_categories_tenant_id` |
| audit columns | — | — | as above |
| `name` | VARCHAR(255) | NO | **No unique constraint** |
| `description` | VARCHAR(255) | YES | |

> **`description` can overflow.** `CategoryRequest` allows up to 500 characters
> (`dto/request/CategoryRequest.java:25`) but the column is `VARCHAR(255)`. A 300-character
> description passes validation and then fails at insert.

> **Name uniqueness is application-only.** `CategoryServiceImpl.create` checks for a duplicate name
> within the tenant first (`CategoryServiceImpl.java:120-127`), but no database constraint backs
> it. Two concurrent creates can both pass the check and both insert.

### `products`

Source: `V5__init_tenant_business_tables.sql:33-53`. Entity: `entities/Product.java`.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | VARCHAR(255) | NO | PK `pk_products` |
| `tenant_id` | VARCHAR(255) | NO | indexed, `idx_products_tenant_id` |
| audit columns | — | — | as above |
| `name` | VARCHAR(255) | NO | |
| `reference` | VARCHAR(255) | NO | UNIQUE `uc_products_reference` — **global, not per tenant** |
| `description` | TEXT | NO | |
| `alert_threshold` | INTEGER | NO | stored, never read by any code |
| `price` | DECIMAL(19,2) | NO | |
| `category_id` | VARCHAR(255) | YES | FK `fk_products_on_category` → `categories(id)` |

> **`reference` is globally unique.** Tenant A creating SKU `IPH-15-001` blocks tenant B from
> using it. Worse, `ProductServiceImpl.checkProductExistance` looks it up with
> `findByReferenceIgnoreCase` (`ProductRepo.java:10`) — a method the tenant filter *does* scope, so
> tenant B's duplicate check finds nothing, and the insert then fails on the global constraint
> with a 409. The check and the constraint disagree about scope.

## Relationships

| From | To | Cardinality | Owning side | Fetch | Cascade | Orphan removal |
|---|---|---|---|---|---|---|
| `User.tenant` | `Tenant` | many-to-one | `User` (read-only: `insertable=false, updatable=false`) | LAZY | none | no |
| `Product.category` | `Category` | many-to-one | `Product` | **EAGER** (JPA default) | none | no |
| `StockMvt.product` | `Product` | many-to-one | `StockMvt` | **EAGER** (JPA default) | none | no |
| `Product.stockMovements` | `StockMvt` | one-to-many, `mappedBy="product"` | `StockMvt` | LAZY | none | no |

Three consequences:

- `User.tenant` is mapped read-only (`User.java:26`), so the association can never be written
  through JPA. `TenantServiceImpl.java:185-186` sets both `tenantId` and `tenant`; only `tenantId`
  reaches the database.
- The two `@ManyToOne` fields have no explicit `fetch`, so they are **EAGER**. Loading a page of
  stock movements loads every product, and each product eagerly loads its category — three
  queries deep per page. With `open-in-view: false` this was presumably the path of least
  resistance. `[INFERRED]`
- No cascade and no orphan removal anywhere. Deleting a `Category` that has products raises a
  foreign-key violation, which `GlobalExceptionHandler` turns into a 409.

**Diagram Brief: Entity relationship map**
Boxes:
  - Tenant — tenants. company_code, email, status, admin_* credentials
  - User — users. username, email, password, role, enabled
  - Category — categories. name, description
  - Product — products. reference, price, alert_threshold
  - StockMvt — stock_mvts. type_mvt, quantity, date_mvt
  - AbstractEntity — mapped superclass. id, tenant_id, audit columns, deleted
Arrows:
  - User -> Tenant : many-to-one, FK on "tenant id", read-only in Java
  - Product -> Category : many-to-one, FK category_id, EAGER
  - StockMvt -> Product : many-to-one, FK product_id, EAGER
  - Product -> StockMvt : one-to-many, mappedBy product, LAZY
  - AbstractEntity -> Tenant : inherited by
  - AbstractEntity -> User : inherited by
  - AbstractEntity -> Category : inherited by
  - AbstractEntity -> Product : inherited by
  - AbstractEntity -> StockMvt : inherited by
Grouping: Tenant and User inside "cross-tenant, always public schema"; Category, Product, StockMvt inside "tenant-scoped business data, filtered by tenant_id"
Layout hint: top-down, AbstractEntity off to one side, inheritance arrows dashed

## `AbstractEntity` and auditing

Six columns are inherited by every table (`entities/AbstractEntity.java:39-64`).

| Field | Column | Filled by | Notes |
|---|---|---|---|
| `id` | `id` | Hibernate `GenerationType.UUID` | `updatable = false` |
| `tenantId` | `tenant_id` | `@PrePersist` from `TenantContext` | throws if absent |
| `createdAt` | `created_at` | `@CreatedDate` | `updatable = false` |
| `updatedAt` | `updated_at` | `@LastModifiedDate` | `insertable = false` — always NULL on insert |
| `createdBy` | `created_by` | `@CreatedBy`, falling back to `"system"` | `updatable = false` |
| `updatedBy` | `updated_by` | `@LastModifiedBy` | `insertable = false` |
| `deleted` | `deleted` | `@PrePersist` sets `false` | |

Auditing is switched on by `@EnableJpaAuditing(auditorAwareRef = "auditorProvider")`
(`config/JpaAuditingConfig.java:14`). `AuditorAwareImpl` reads the Spring Security principal
(`:26-55`) and handles two shapes, because the principal differs by code path:

- during **login** it is the `User` entity (a `UserDetails`), so the username is stored;
- on **every later request** `JwtAuthenticationFilter` puts the **user-id String** in the context
  (`JwtAuthenticationFilter.java:50`), so `created_by` stores a UUID, not a username.

So `created_by` is inconsistent: a username for rows written during login, a UUID otherwise, and
`"system"` when no principal exists.

## Enums

All three persist as `VARCHAR` via `@Enumerated(EnumType.STRING)`, with a CHECK constraint
mirroring the Java values.

| Enum | Column | Values | Constraint |
|---|---|---|---|
| `TenantStatus` | `tenants.status` | `PENDING`, `ACTIVE`, `SUSPENDED`, `INACTIVE` | `chk_tenant_status` (V1:34), `chk_tenants_status` (V2:2-6) |
| `UserRole` | `users.role` | the 5 `ROLE_*` values | `chk_user_role` (V1:75-81), `chk_users_role` (V2:9-18) |
| `TypeMvt` | `stock_mvts.type_mvt` | `IN`, `OUT` | `chk_type_mvt` (V5:70) |

**`V2__add_enum_checks.sql` is redundant.** V1 already created equivalent CHECK constraints under
slightly different names (`chk_tenant_status` vs `chk_tenants_status`). V2 guards with
`IF NOT EXISTS` on its own name, so the guard never fires and both constraints end up on the
table. Harmless, but every status write is now validated twice.

Using `EnumType.STRING` plus a CHECK means adding a role requires a migration as well as a Java
change. `[INFERRED]` — the trade is readable data and a database-level guarantee, against the
cost of keeping two lists in step.

## Migration strategy

| File | Targets | Runs | What it does |
|---|---|---|---|
| `common/V1__init_Common_tables.sql` | `public` | startup | Creates `tenants` and `users` with constraints and the `"tenant id"` FK |
| `common/V2__add_enum_checks.sql` | `public` | startup | Adds duplicate status and role CHECK constraints |
| `common/V3__seed_demo_data.sql` | `public` | startup | Seeds the `acme-corp` tenant and the `admin` user, both `ON CONFLICT DO NOTHING` |
| `common/V4__fix_demo_admin_password.sql` | `public` | startup | Resets the demo admin's BCrypt hash — the V3 hash matched no password |
| `common/V5__init_tenant_business_tables.sql` | `public` | startup | Creates `categories`, `products`, `stock_mvts` plus a `tenant_id` index on each |
| `tenant/V1__init_For_tenat_DB.sql` | `tenant_<code>` | **on tenant approval only** | Creates the same three business tables inside the new schema |

Startup run: `spring.flyway.*` in `application.yml:37-43` — `baseline-on-migrate: true`,
`validate-on-migrate: true`, history in `public.flyway_schema_history`.

Per-tenant run: a programmatic `Flyway` built in `ProvisioningServiceImpl.runTenantMigrations`
(`:110-126`) with `schemas(schemaName)`, `defaultSchema(schemaName)`,
`locations("classpath:db/migration/tenant")` and its own `flyway_schema_history` inside that
schema. On any failure the whole schema is dropped `CASCADE` (`:98-108`).

**`common/V5` and `tenant/V1` define the same three tables.** V5 is the one that matters — it
creates them in `public`, where the application actually reads and writes. `tenant/V1` only ever
populates schemas nothing queries. The two files can drift apart with no visible symptom.

`provisionTenant` runs with the caller's transaction suspended
(`@Transactional(propagation = NOT_SUPPORTED)`), because `CREATE SCHEMA` on one connection and
Flyway on a second deadlock if the first is still uncommitted. `[DOCUMENTED]` — javadoc on
`ProvisioningServiceImpl.provisionTenant`.

## Indexes, keys and constraints

| Kind | Present on | Serves |
|---|---|---|
| Primary key | all 5 tables, on `id` | `findById` |
| Index | `categories.tenant_id`, `products.tenant_id`, `stock_mvts.tenant_id` (V5:77-79) | the `tenant_id = ?` predicate the filter adds to every query |
| Unique | `tenants`: `company_code`, `email`, `admin_email`, `admin_username` | registration duplicate checks |
| Unique | `users`: `username`, `email` | login lookup, duplicate checks |
| Unique | `products.reference` | SKU duplicate check (global, see above) |
| Foreign key | `users."tenant id"`→`tenants.id`, `products.category_id`→`categories.id`, `stock_mvts.product_id`→`products.id` | referential integrity |
| Check | status, role, `type_mvt` | enum safety |

**Missing indexes that the query patterns ask for:**

- `users.tenant_id` — `findAllByTenantIdAndNotDeleted` (`UserRepo.java:31`) filters on the tenant
  association every time the user list is read.
- `tenants.status` — `findAllByStatus` (`TenantRepo.java:16`) backs `GET /tenants/pending`.
- `stock_mvts.product_id` and `products.category_id` — Postgres does not index the referencing
  side of a FK automatically, and both are joined eagerly on every read.
- `deleted` appears in the filter predicate on every query but is never indexed. A composite
  `(tenant_id, deleted)` would match the actual predicate better than `tenant_id` alone.

# Data Model Risks and Improvement Candidates

Suggestions only.

| # | Risk | Why it matters |
|---|---|---|
| 1 | **`users` has two tenant columns**, `tenant_id` (used, no FK) and `"tenant id"` (FK, unmapped). | The column the app relies on has no referential integrity; the one that does is dead. A space in a column name also forces quoting forever. |
| 2 | **`tenant_id` means a company code on `tenants` and a UUID everywhere else.** | Any future join or schema-mode port has to special-case it. |
| 3 | **`products.reference` is globally unique but checked per tenant.** | A valid SKU in tenant B fails with a 409 it cannot explain. Make the constraint `(tenant_id, reference)`. |
| 4 | **`CategoryRequest` permits 500 chars into a `VARCHAR(255)`.** | Validation passes, insert fails, caller gets a 500. |
| 5 | **Category name uniqueness has no database constraint.** | Concurrent creates both succeed. |
| 6 | **`users.username` / `email` unique globally.** | Blocks two tenants from having the same username, and leaks existence across tenants. |
| 7 | **Both `@ManyToOne` fields are EAGER.** | Listing stock movements triggers product and category loads per row. `LAZY` plus an entity graph would fix it. |
| 8 | **`V2` duplicates `V1`'s CHECK constraints.** | Dead migration; two constraints doing one job. |
| 9 | **`V5` and `tenant/V1` define the same tables in two files.** | Guaranteed drift; only one is reachable. |
| 10 | **`created_by` holds a username sometimes and a UUID other times.** | The audit trail cannot be read consistently. |
| 11 | **No index on `users.tenant_id`, `tenants.status`, or the FK columns.** | Every one backs a query that exists today. |
| 12 | **Deletes are hard deletes despite a `deleted` column and a `deleted = false` predicate.** | The soft-delete design is half-built — see 02, risk 8. |
